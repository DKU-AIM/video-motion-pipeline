# 농구 영상: 정확도·다중 구간 회수·비용 실험

> 현재 실행은 [1차 모델 비교](BASKETBALL_QUICK_COMPARISON.md)로 축소했다: 모델 8개 × 쿼리 4개 = 32회, 강제 시간 제한 없음. 아래 전체 계획은 후속 실험용이며 현재 실행 중이 아니다.

## 입력과 목적

- 원본: `/home/elicer/aim-workspace/inputs/grounding/2026_AsianGames_men's_basketball_final.mp4`
- 비디오 스트림 약 222.56초(컨테이너 222.63초), 1920×1080, 약 29.97fps, HEVC, 약 83.4MiB.
- 10초 간격 대표 프레임에서 경기 장면, 선수 클로즈업, 벤치 반응, 자막/전환을 확인했다. 프레임 표본 검토는 모든 사건의 존재·횟수 검수가 아니다. 파일명의 경기명·연도를 외부 사실로 검증한 것은 아니다.
- 질문: 올바른 구간인가? 반복되는 같은 사건을 얼마나 빠짐없이 찾는가? 그 성능에 필요한 시간·메모리는 얼마인가?
- 이 한 편에 대한 탐색 실험이다. 일반 성능/모델 전체 순위로 확대하지 않는다. 추후 다른 경기 영상을 최종 검증용으로 분리한다.

## 정답부터 고정하기

`experiments/basketball/queries.json`에는 8개 개념 × 영어 표현 2개가 있다. 슛, 어두운 유니폼의 슛, 자유투, 벤치 환호, 얼굴 클로즈업, 덩크, 축구, 수영이다. 특히 자유투·덩크·부재 후보의 실제 존재 여부는 미확정이다.

`annotations.template.json`을 workspace로 복사하고 전체 영상을 보면서 쿼리별 모든 `[시작초, 종료초]`를 적는다. 시간은 **업로드된 파일의 재생 시간**이며 화면 속 경기 시계가 아니다.

- 샷 경계: 보이는 슈팅 동작 시작 → 보이는 결과 또는 화면 전환. 공을 잡고 있는 구간 전체를 슛으로 라벨링하지 않는다.
- 리플레이: 비디오 내 서로 다른 시점에 다시 보이면 별도 구간. 실제 경기의 중복 사건 수와 비디오 속 등장 횟수를 구분한다.
- 여러 사건 사이의 무관한 시간을 한 구간으로 묶지 않는다.
- 전체 영상을 끝까지 확인한 쿼리만 `reviewed: true`. 확인 결과 없음은 `reviewed: true, spans: []`.
- `reviewed: false, spans: []`는 미확인이며 정답 없음이 아니다. 평가기가 제외한다.
- 동일 개념의 두 표현은 같은 정답을 사용한다. 애매한 사례는 notes에 기록한다.
- 가능하면 두 사람이 독립 라벨링하고 경계·포함 여부를 합의한다. 모델 결과를 먼저 보고 정답을 맞추지 않는다.

## 비교 단계 — 전체 조합을 한 번에 돌리지 않는다

| 단계 | 목적 | 설정/분량 |
|---|---|---|
| 0. 파일럿 | 코드·메모리·출력 형식 확인 | TimeLens2-4B, 전체 영상, 슛/벤치/클로즈업 각 1개 표현 = 3회 |
| 1. 기본 비교 | 모델별 원래 출력 행동 관찰 | TimeLens2-4B, TimeLens2-8B, TimeLens-8B, Time-R1-7B × 8개 개념 첫 표현 = 32회 |
| 2. 다중 출력 지시 | 모델 능력과 기본 프롬프트 영향 분리 | 같은 네 모델/8개 쿼리에 all-json 지시 = 32회. native와 별도 집계 |
| 3. 쿼리 민감도 | 문장만 바꿨을 때 변화 | 상위 후보 2개에서 8개 개념 × 2개 표현 = 후보당 16회 |
| 4. 샘플링·예산 | 작은 공/짧은 슛의 누락 원인 탐색 | 후보 1~2개에서 아래 요인별 실험. 한 번에 한 축 변경 |
| 5. 분할 검색 | 긴 입력에서 놓치는 장면 회수 | 전체 입력 vs 60초/10초 중첩 vs 30초/5초 중첩. 전체 탐색 비용과 사건 회수율 비교 |
| 6. 시간 재측정 | 워밍업/편차 분리 | 확정된 조건을 repeat=3으로 반복. 첫 호출과 이후 호출을 따로 집계 |

현재 추가한 실행기는 0~4/6의 단일 영상 측정을 지원한다. 5단계 자동 클립 생성·좌표 복원·중복 제거는 **설계 단계이며 실행기에 아직 포함되지 않았다**. CLI에 window 옵션이 있는 것으로 가정하지 않는다. 5단계는 다음 규칙으로 추가한다: 로컬 구간에 클립 시작 시간을 더해 전역 시간으로 바꾸고, 인접 창의 중복만 고정 기준(tIoU ≥ 0.5)으로 제거한다. 원본 창별 결과도 남긴다. 창 경계에서 잘린 사건을 검수하고, 합치기 전후 점수를 모두 보고한다. 모델이 한 응답에 여러 구간을 생성한 능력과 분할 시스템이 여러 응답을 모은 능력을 별도 열로 보고한다.

확장 후보: TimeLens-7B, Time-R1-3B, Qwen3-VL-8B, Qwen2.5-VL-7B. 기존 모델 registry에 있고 실행기 `--model`로 선택 가능하다. 모든 후보의 실제 추론 호환성은 아직 검증하지 않았다. Qwen 원본은 fine-tuning 전 대조군이다.

## 다중 구간 지원 판정 시 주의

TimeLens2-4B 공식 예제는 ALL time spans를 JSON 배열로 요청한다:
https://huggingface.co/MCG-NJU/TimeLens2-4B

현재 팀 코드의 TimeLens2 계열 프롬프트/파서는 배열을 지원한다. 반면 기존 TimeLens·Time-R1 파서는 마지막 한 쌍만 반환한다. 따라서 기존 CLI 결과만 보고 해당 모델이 여러 구간을 못 생성한다고 결론내리면 안 된다.

새 실행기는 `raw`, `legacy_spans`, 모든 최종 응답 구간을 읽은 `spans`를 함께 저장한다. Time-R1의 `<think>` 내 시간은 최종 예측에 포함하지 않는다. all-json 조건은 학습 당시의 기본 지시와 다른 실험이며, 원래 프롬프트 성능과 섞지 않는다. JSON `[]`와 해석 실패(unparsed)를 구분한다.

판정에는 다음 세 가지가 모두 필요하다:
1. 서로 떨어진 구간을 2개 이상 실제로 반환한다.
2. 그것들이 서로 다른 정답 사건과 일대일로 대응한다(중복 예측 제외).
3. 다른 정답 사건의 누락과 없는 사건의 오탐까지 함께 측정한다.

## 고정값과 파라미터 축

초기 전체 영상 기준: FPS 1, max_frames 256, visual total_tokens 16384, max_new_tokens 1024, SDPA, BF16, greedy decoding. 전체 영상에서 요청 프레임 수는 약 223개지만 라이브러리 정렬/샘플링 결과는 달라질 수 있다.

- FPS 실험: 0.5 / 1 / 2. 이 묶음은 max_frames=512, total_tokens=32768을 고정한다. 2fps에서 프레임 상한 때문에 샘플이 줄어드는 혼동을 피한다.
- 비주얼 예산 실험: FPS 1, max_frames 256을 고정하고 8192 / 16384 / 32768. 프레임당 최소 해상도 때문에 작은 예산이 그대로 지켜지지 않을 수 있으므로 실제 input_tokens와 video_grid_thw를 반드시 비교한다.
- 출력 길이: 256 / 1024 / 2048. 출력 상한 도달 여부를 확인한다. 길이 부족으로 잘린 결과를 다중 검색 능력 부족으로 해석하지 않는다.
- 문장: 동일 개념의 영어 paraphrase 비교를 먼저 한다. 한국어/상세 지시문/선수 번호는 별도 실험으로 추가한다. 선수 이름이나 성공한 3점슛처럼 추가 판별이 필요한 쿼리는 초기에 섞지 않는다.
- 비주얼 total_tokens는 입력 전체의 엄격한 토큰 상한이 아니라 픽셀 예산이다. OOM도 결과로 남기며, 예산을 몰래 낮춰 재시도하지 않는다.

## 정확도 평가

평가기는 정답과 예측을 tIoU 임계값 0.3 / 0.5 / 0.7에서 최대 개수 일대일 매칭한다. 한 예측이 여러 정답을 맞힌 것으로 세지 않는다. 같은 사건의 중복 예측은 오탐으로 남는다. 잘못된 범위도 오탐이며 경계를 잘라서 유리하게 보정하지 않는다.

`evaluation.csv`에는 사건별 Precision/Recall/F1, TP/FP/FN, 구간 개수 절대오차, 모든 사건 회수 여부, 부재 쿼리 정답 여부를 기록한다. 부재 정답에는 사건 Recall/F1을 억지로 정의하지 않는다. 부재 성공은 정상 추론의 명시적 JSON `[]`에만 부여한다. 실행 실패/파싱 실패는 부재 성공이 아니다.

다중 사건 쿼리의 Recall과 전체 회수율을 주 지표로 보고 Precision을 함께 본다. 정답이 하나인 쿼리는 별도 집계한다. 단일 IoU나 반환 개수만으로 순위를 매기지 않는다. 이 단계에서는 쿼리별 CSV를 보고, 서로 다른 프롬프트/설정/반복을 하나의 평균으로 섞지 않는다.

## 자원·시간 관측

"한 턴"은 **한 모델·한 설정에서 영상 1개 + 쿼리 문장 1개를 넣어 응답 1개를 받는 것**이다. 분할 검색에서는 클립별 호출과 전체 쿼리 완료 시간이 별개다.

- `load.json`: 가중치 다운로드를 포함한 모델 로드 시간, 가능한 경우 모델 commit. 첫 다운로드와 캐시 로딩은 별도 실행으로 비교한다.
- `summary.csv`, `results.jsonl`: 전처리(디코딩/샘플링/입력 전송), GPU 동기화 후 생성 시간, 텍스트 디코딩/파싱, 총 응답 시간; 입력/출력 토큰 수; 출력 길이 상한 도달 여부; 실제 비주얼 grid; 쿼리별 GPU peak allocated/reserved GiB. 로깅 시간은 응답 시간에서 제외한다.
- `resources.jsonl`: 약 1초 간격 프로세스 RSS, 프로세스 CPU%(코어 1개=100%, 다중 코어면 100 초과), 단계, NVIDIA 조회 원문/단위. 샘플링 시각과 쿼리 종료 시각으로 연결한다.
- MIG에서는 물리 GPU 사용률이 N/A일 수 있다. GPU 전력/보드 메모리는 다른 MIG 사용자까지 포함할 수 있으므로 **이번 모델의 소비 전력/에너지로 계산하지 않는다**. 측정 불가를 0으로 취급하지 않는다.
- 모델 하나를 로드해 여러 쿼리에 재사용한다. 첫 쿼리(cold_query=true)와 이후 반복은 따로 비교한다. repeat=3도 greedy이므로 다양한 답을 샘플링하는 실험은 아니다.
- `settings.json`, `prompt-template.txt`, `pip-freeze.txt`, `gpu.txt`, `code-commit.txt`로 조건을 보관한다. 원격 revision을 설치 단계에서 완전히 고정한 패키지는 아니다.

## 실행

아래는 모두 레포 루트에서 실행한다. 기본 실행은 파일럿 3회이며 모든 모델 다운로드를 한 번에 시작하지 않는다.

```bash
bash scripts/run_basketball_probe.sh
```

결과 경로는 시작 시 출력된다. 같은 폴더를 덮어쓰지 않으며 모델별 실행 폴더가 분리된다.

기본 비교 한 모델(8개 첫 표현):

```bash
bash scripts/run_basketball_probe.sh --model timelens2-8b \
  --ids shot dark_shot free_throw bench closeup dunk football swimming
```

같은 모델의 모든 구간 지시 조건:

```bash
bash scripts/run_basketball_probe.sh --model timelens2-8b --prompt all-json \
  --ids shot dark_shot free_throw bench closeup dunk football swimming
```

쿼리 변형과 3회 반복(3개 개념 × 2표현 × 3반복 = 18회):

```bash
bash scripts/run_basketball_probe.sh --model timelens2-4b \
  --ids shot bench closeup --variants all --repeat 3
```

정답 복사(기존 파일을 덮어쓰지 않음):

```bash
cp -n experiments/basketball/annotations.template.json \
  "$HOME/aim-workspace/inputs/grounding/basketball_annotations.json"
```

정답 작성 후 평가. RUN_DIR에 실제 추론 결과 폴더를 입력한다:

```bash
read -r -p "결과 폴더의 절대 경로: " RUN_DIR
"$HOME/aim-workspace/grounding_env/bin/python" grounding/evaluate_basketball.py \
  --run "$RUN_DIR" \
  --annotations "$HOME/aim-workspace/inputs/grounding/basketball_annotations.json"
```

## 작성 시 검증 범위

영상 메타데이터/대표 프레임 확인, 파서·다중 사건 매칭·부재 판정 테스트, CLI 및 shell 문법 점검까지 수행했다. 새 농구 계측 실행기로 가중치를 다운로드하거나 GPU 전체 추론을 실행하지 않았다. 정답 구간은 아직 작성되지 않았으며, 현재 어떤 모델이 이 농구 영상에서 가장 잘 찾는다는 결과는 없다.

## 전체 모델 자동 실행 (추가)

```bash
bash scripts/run_basketball_all.sh
```

지원 모델 8종을 순차 실행한다. 모델별 조건 9개로 총 72개 세션, 쿼리 호출은 1,664회다. native/all-json 기준 조건은 16문장 × 3반복, 나머지 7조건은 16문장 × 1회다. FPS 비교 묶음은 비주얼 예산 32768과 최대 프레임 512를 고정한다. 기본 비교가 모든 모델에서 먼저 진행되고 파라미터 비교가 뒤따른다. 영상 분할 실험은 포함하지 않는다.

- 계획만 확인: `bash scripts/run_basketball_all.sh --dry-run`
- 결과: `~/aim-workspace/results_grounding/basketball_all/`
- `progress.md`: 약 10초 간격 세션 상태와 기록된 호출 수.
- `all_trials.csv`: 모델·조건 열을 포함한 전체 쿼리 결과 통합본. 정확도 라벨은 아직 없으므로 정확도 순위는 계산하지 않는다.
- `state.json`, `plan.json`: 재개용 실행 상태와 고정 계획·입력/코드 해시.
- 모델/조건 폴더의 `attempt_001.log`: 해당 실행의 stdout/stderr. attempt 폴더에는 상세 자원·응답 기록.
- 모델은 자식 프로세스로 하나씩 실행한다. 프로세스가 끝나 GPU 메모리가 반환된 뒤 다음으로 넘어간다.
- 실패/OOM은 기록하고 다음 조건을 진행한다. 설정값을 자동 변경하지 않는다.
- 세션당 기본 제한은 다운로드 포함 6시간이다. `--timeout-hours`로 변경한다.
- 남은 디스크가 5GiB 미만이면 중단한다. 다운로드할 모델 하나의 크기를 미리 보장하는 검사는 아니다.
- 같은 명령 재실행 시 성공 세션은 건너뛰고 중단된 세션은 새 attempt에서 처음부터 실행한다. 이미 실패한 세션을 재시도하려면 `--retry-failed`를 추가한다. 과거 attempt는 보존한다.
- 계획/입력/코드가 바뀌면 기존 결과와 섞지 않도록 거부한다. 다른 실험은 `--out`으로 새 경로를 지정한다.
- 동시에 같은 workspace의 배치 두 개가 실행되지 않도록 잠근다. 사용자가 따로 실행하는 단일 모델 CLI까지 잠그는 것은 아니다.

SSH 연결과 분리해 실행하려면 tmux를 사용한다. 이미 `basketball-all` 세션을 시작했다면 새로 실행하지 말고 접속한다.

```bash
tmux attach -t basketball-all
```

Ctrl+B를 누르고 D를 누르면 실행을 유지한 채 나온다. Ctrl+C는 현재 실험을 중단한다. 중단 후 위 배치 명령으로 재개할 수 있다.
